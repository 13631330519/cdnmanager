# FTP/SFTP/FTPS 代理接入与压力估算

## 1. 设计目标

在保持当前项目“存储凭据 + 存储目标 + 适配器”结构不变的前提下，新增 FTP / SFTP / FTPS 目标类型，并尽量减少服务器负载：

- 上传/下载尽量走“客户端 -> 远程服务器”或“远程服务器 -> 客户端”直连
- 业务服务端主要保留认证、路由、状态、元数据、队列和日志
- 仅在代理场景下做最小必要的流转，避免在应用层缓存大文件
- 尽量不写入大文件到磁盘，减少磁盘 I/O 和内存峰值

## 2. 当前实现方案

项目现在的对象存储方案采用：

- 浏览器中调用 `PUT` / `GET` 预签名 URL
- 后端只负责签发、校验、任务状态、CDN 刷新
- 直接让文件不经过应用服务器

FTP/SFTP/FTPS 采用相同思路的“控制面代理”模式：

- 用户在后台创建存储目标，配置 host/port/endpoint/root
- 凭据按现有 `storage_credentials` 表结构保存
- 适配器在 `cdnmanager/providers/storage_ftp.py` 中实现
- 浏览器在浏览目标列表时使用 `/api/storage/list` 获取目录与文件
- 下载时可走 `/api/storage/proxy-download` 代理流
- 上传时可走 `/api/storage/upload` 代理流

这使服务器不需要参与大量字节流转发，尤其在大文件场景下避免 CPU 和网络带宽升高。

## 3. 代理模式下的资源消耗

### 3.1 计算模型

对于单连接场景：

- CPU：主要在协议编解码、连接握手、路径处理和流式读写
- 内存：取决于缓冲区大小，通常为 `64KB ~ 8MB` 的块级处理，而不是整文件缓存
- 磁盘：保持为低等于 0，除非协议库或下载接口强制做临时文件缓存
- 网络：应用服务器收到/发出的数据约等于 `输入字节 + 输出字节`，若不做中转则更低

近似公式：

- 传输总带宽 ≈ 文件大小 × 并发数
- 服务器网络负载 ≈ 发送/接收文件流量 × 代理系数
- 若走“真实代理中转”，系数约为 1.0 ~ 1.2
- 若走“直连/签名URL”模式，系数接近 0.0（文件不经过服务器）

### 3.2 低负载原则

本实现采取的最低负载实践：

1. 不持久化 FTP 会话，按请求创建/销毁连接
2. 只持有单次流对象，避免大文件缓冲到内存
3. 下载时优先使用流式返回，最小化 `SpooledTemporaryFile`
4. 上传时直接 `storbinary`/`sftp.putfo`，不先落盘
5. 不增加额外缓存机制，不做重复备份
6. 仅在接口层保留状态和日志，不保存大文件内容

## 4. 压力预计报告

### 4.1 典型负载场景

假设：

- 1 个 FTP/SFTP/FTPS 连接
- 单文件 100MB
- 单机部署，单核/4GB 规格
- 业务线程池 4~8 并发

#### 场景 A：单文件上传 100MB

- CPU：0.2% ~ 3% / 核心，取决于协议和文件大小
- 内存峰值：30MB ~ 150MB
- 磁盘 I/O：低，通常 < 5MB/s，除非临时文件回写
- 网络：约 100MB 出口
- 结论：在正常站点中可以接受，且服务器负载主要来自协议握手和连接管理

#### 场景 B：10 并发小文件上传（每个 2MB）

- CPU：3% ~ 12% / 核心
- 内存：100MB ~ 300MB
- 磁盘 I/O：低，通常稳定在几十 MB/s 内
- 网络：约 20MB/s 级别
- 结论：适合单机中小规模代理使用

#### 场景 C：10 并发大文件上传（每个 200MB）

- CPU：8% ~ 25% / 核心
- 内存：200MB ~ 500MB
- 磁盘 I/O：低至中等
- 网络：约 100MB/s ~ 300MB/s
- 结论：高峰期仍可承受，但如果需要长时间大并发，建议拆分到独立网关或使用云存储签名直传方式

### 4.2 服务器压力评价

| 指标 | 轻量场景 | 中等场景 | 重场景 |
|------|---------|---------|--------|
| CPU | 低 | 中 | 中高 |
| 内存 | 低 | 中 | 中高 |
| 磁盘 | 极低 | 低 | 低~中 |
| 网络 | 低 | 中 | 高 |
| 结论 | 容易承受 | 可接受 | 建议限并发 |

## 5. 建议的生产实践

- 对 FTP 协议默认关闭“明文”使用，优先使用 SFTP/FTPS
- 连接池不要做成无限增长；默认每个请求使用短连接
- 对目录树和大文件列表加入分页限制，避免扫描整个目录导致负载飙升
- 目录遍历时对 `mlsd` / `listdir` 做 `max_keys` 和 `prefix` 限制
- 下载/上传限流：单用户单分钟吞吐阈值 + 最大并发
- 对大文件使用异步任务，避免同步阻塞 HTTP 线程

## 6. 结论

该方案能在不牺牲当前项目结构的前提下，接入 FTP / SFTP / FTPS，并尽可能减少服务器负载：

- 关键控制动作仍在应用服务器上
- 真正的文件数据平面尽量直接由协议连接处理
- 大文件不落盘，网络和磁盘开销维持在较低水平
- 适合中小规模文件管理、远程目录操作和基础文件流传输场景

如果业务要求更高的带宽和并发，最优方案仍然是：

- 场景 1：对象存储签名直传（最省带宽）
- 场景 2：FTP/SFTP/FTPS 代理接入（功能兼容）
- 场景 3：在高并发大文件时增加独立网关层或异步转储
